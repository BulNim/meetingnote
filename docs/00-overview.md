# 00 - Overview

MeetingNote - 회의록 자동 정리 풀스택 웹 앱

## 6개 파일 지도

| 파일명 | 역할 | 알 수 있는 것 |
|---|---|---|
| `00-overview.md` | 전체 지도 | 어느 문서를 어떤 순서로 읽는지 |
| `01-product.md` | WHY | 목표, 페르소나, MVP 범위, 범위 외, 성공 기준 |
| `02-specs.md` | WHAT | 데이터 모델, 3항목 구분 기준, REST API, 검증 |
| `03-design.md` | HOW | 기술 선택과 트레이드오프, 의존성 정책 |
| `04-tasks.md` | 언제 | Phase 별 구현 순서와 체크리스트 |
| `05-conventions.md` | 규율 | 명명 규칙, 금지 항목, 테스트 매트릭스, 커밋 규칙 |

## 읽는 순서

```
00 > 01 > 02 > 03 > 04 > 05
```

의존 방향은 위에서 아래로만 흐른다. 상위 결정이 하위의 입력이 되고,
역방향 영향은 금지한다. 컨벤션 때문에 제품 방향이 바뀌는 일은 없어야 한다.

## 왜 이렇게 나누는가 - 관심사 분리

한 파일에 목적 · 기능 · 기술 · 순서 · 규약을 모두 적으면 무엇을 고칠 때
어디를 봐야 하는지 알 수 없다. 관심사를 갈라 두면 바뀐 관심사에 해당하는
문서 하나만 고치면 되고, 나머지는 그대로 둔다.

- WHY(01) 가 바뀌면 WHAT(02) 을 다시 본다
- WHAT(02) 이 바뀌면 HOW(03) 와 순서(04) 를 다시 본다
- 규약(05) 이 바뀌어도 제품 방향(01) 은 바뀌지 않는다
