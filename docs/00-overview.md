## 화면

화면은 4종이다.

1. **목록** - 저장된 회의록을 모아 본다
2. **넣기** - 녹음 · 음성 파일 · 텍스트를 넣어 회의록을 만든다
3. **상세** - 회의록 한 건의 받아쓰기 · 정리 결과를 본다
4. **할 일** - 회의록에서 뽑아낸 할 일을 모아 본다

**배치와 요소 이름은 `docs/화면구성.pdf` 를 따른다. 요소의 id 는 그 파일에 적힌 그대로 쓴다.**
임의로 id 를 짓거나 바꾸지 않는다.

## 디자인

- UI 는 **맥OS 스타일**로 만든다
- CSS 라이브러리는 **Tailwind** (CDN) 를 쓴다
- 깔끔하고 모던하게 - 여백을 넉넉히, 장식은 줄인다

## 왜 이렇게 나누는가 - 관심사 분리

**관심사 분리(Separation of Concerns)** 는 성격이 다른 내용을 서로 다른 곳에 두어,
한 가지를 바꿀 때 다른 것이 함께 흔들리지 않게 하는 원칙이다.
코드에 쓰는 원칙을 문서에도 그대로 적용했다.

| 관심사 | 바뀌는 이유 | 담는 곳 |
|---|---|---|
| 무엇을 · 왜 만드는가 | 사업 · 사용자 요구가 바뀔 때 | `01-product.md` |
| 시스템이 어떻게 동작하는가 | 기능 · 데이터 구조가 바뀔 때 | `02-specs.md` |
| 사용자에게 어떻게 보이는가 | 화면 · 디자인이 바뀔 때 | `03-design.md` |
| 어떤 순서로 만드는가 | 일정 · 우선순위가 바뀔 때 | `04-tasks.md` |
| 코드를 어떻게 쓰는가 | 팀 규칙이 바뀔 때 | `05-conventions.md` |

이렇게 나누면 얻는 것:

- **바꿀 곳이 하나다** - 화면이 바뀌면 `03-design.md` 만 고친다. 명세와 규칙은 그대로다
- **필요한 것만 읽는다** - API 를 고칠 때는 `02-specs.md` 만 보면 된다
- **어긋남이 드러난다** - 지시가 문서와 다르면 어느 문서 어느 조항과 부딪치는지 바로 짚을 수 있다
- **코드 구조와 맞물린다** - `02-specs` ↔ `backend/`, `03-design` ↔ `frontend/` 로 대응해 문서와 코드를 함께 따라갈 수 있다
